# 要件定義書: エンジニア縛りボブジテン Webアプリ (v2)

## 0. 改訂履歴

| 版  | 主な変更点                                                                                                                                                                                                                            |
| --- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| v1  | 初版                                                                                                                                                                                                                                  |
| v2  | ホスティングを Cloudflare Workers (Static Assets) に変更 / Durable Objects・WebSocket をフェーズ2の技術選定事項へ降格 / お助け機能を全面刷新 / 重複排除を口頭ルール化しMVPから除外 / フェーズ2の優先度を再設定 / 「検討課題」章を新設 |

## 1. はじめに

本ドキュメントは、フロントエンドエンジニア約7名のオンライン飲み会用レクリエーション「エンジニア縛りボブジテン」Webアプリの開発要件を定義する。
フェーズ1（MVP）とフェーズ2（エンハンス）に分け、段階的な開発とリリースを前提とする。

### 1.1. フェーズの位置づけ

- **フェーズ1（MVP）:** アプリは「出題のサポート」に特化する。通信同期は行わず、**各参加者が自分の端末で個別にアプリを開く**。ゲーム進行の管理は参加者の口頭運用に委ねる。
- **フェーズ2:** ゲーム進行の管理をアプリ側に移し、「ホストが手動で管理しなくても成立するアプリケーション」としての完成度を高める。

### 1.2. フェーズ2を実施する動機（記録）

フェーズ2の機能群は、ホスト1名が手元で管理すれば運用上は代替可能である。それでもアプリ側で実装する理由は以下の2点であり、意思決定の根拠として明示的に記録しておく。

1. **プロダクト観点:** ホストの手作業に依存する状態は「アプリとして不十分」である。得点・使用済みステータス・終了判定はアプリが管理すべき責務と位置づける。
2. **技術的動機:** 同期型Webアプリケーションの実装そのものに開発者の関心がある。

## 2. システム構成・技術スタック

### 2.1. フェーズ1（MVP）

MVPは通信同期を行わないため、静的ホスティングのみで完結する。

- **フロントエンド:** React + Vite + TypeScript（SPA構成）
- **スタイリング:** Tailwind CSS 等のユーティリティファーストCSSフレームワーク
- **ホスティング:** **Cloudflare Workers（Static Assets）**
  - Cloudflare は静的アセット配信とSSRの双方に対応した現在、新規プロジェクトは Pages ではなく Workers から始めることを公式に推奨しており、今後の投資・機能開発も Workers に集約される方針を明言している。
  - また Pages 上のアプリから Durable Objects を利用する場合は別途 Worker を立てる必要があり、フェーズ2で構成が二重化する。フェーズ1から Workers に置くことで、フェーズ2は同一デプロイの延長として実装できる。
  - 静的アセットへのリクエストは課金対象外であり、MVP段階のランニングコストは $0 を維持できる。
- **データ管理:** お題データはフロントエンドの `.ts` ファイル内で静的データとして管理する（詳細は 3.1）。

### 2.2. フェーズ2

**フェーズ2の技術スタックは本ドキュメントでは確定しない。**

v1 では Cloudflare Workers + Durable Objects + WebSocket を前提として記載していたが、これは同期対象となる状態モデルが未定義のまま転送手段を先に固定するものであり、順序として不適切であった。

フェーズ2の技術選定は **4.4（リアルタイム同期）に着手する時点で、4.1〜4.3 で確定した状態モデルを入力として** 行う。候補としては Cloudflare Workers + Durable Objects（WebSocket）を有力視するが、選定時点で改めて評価する。

なお **4.1〜4.3 は同期を伴わないため、MVPと同じ静的ホスティング構成のまま実装可能**である（ホストが自端末でスコアボード画面を操作する形態）。ランニングコストが発生しうるのは 4.4 以降である。

## 3. 機能要件（フェーズ1: MVP）

### 3.1. お題データ

`.ts` ファイルにて定数として保持する。

```ts
type Topic = {
  id: string;
  word: string; // カタカナ表記
  difficulty: 1 | 2 | 3;
  category: Category; // お助け機能「カテゴリ公開」で使用
  relatedWords: string[]; // お助け機能「関連語ホワイトリスト」で使用（3〜5語）
};

type Category =
  | "マークアップ・スタイル"
  | "言語・文法"
  | "ライブラリ・フレームワーク"
  | "ビルド・開発環境"
  | "通信・データ"
  | "バージョン管理"
  | "描画・パフォーマンス"
  | "その他";
```

- `relatedWords` には、お題の説明に使えると助けになるカタカナ語を人力またはAI生成で付与する。
- **`relatedWords` にお題自身と部分一致する語を含めてはならない。** フロントエンド用語は複合語が支配的（例:「ローカルストレージ」「サーバーコンポーネント」）であり、完全一致の除外だけでは不十分である。この制約は自動テストで保証する（5章参照）。

### 3.2. お題提示機能

- **お題ピック（ガチャ）機能:**
  - 「お題を引く」ボタン押下で、難易度1〜3の単語がランダムに1つずつ（計3つ）抽出され、画面に表示される。
  - 各候補には難易度を併記する。
- **お題選択機能:**
  - 抽出された3つから出題者が1つを選択する。選択後、その単語が大きく表示された「出題中」画面へ遷移する。
- **引き直し:**
  - 「出題中」画面から「引き直す」操作で 3.2 の先頭に戻れること。既出語との重複時（3.4.1）およびパス券使用時（3.3.4）に使用する。

### 3.3. お助け機能

MVPでは使用回数のシステム管理は行わず、**画面表示と自己申告ベース**で運用する。

#### 3.3.1. カテゴリ公開

- 「出題中」画面に、お題の `category` を表示するボタンを配置する。
- 押下するとカテゴリが表示され、出題者はそれを口頭で宣言できる。
- 回答者の探索空間を直接狭めるため、緩和策として最も効果が高い。

#### 3.3.2. 関連語ホワイトリスト

- 「出題中」画面に「ホワイトリストを見る」ボタンを配置する。
- 押下すると、当該お題の `relatedWords` が表示される。表示された語は説明に使用可能となる。
- **v1のランダム抽出方式から変更した。** お題と無関係な語を解禁しても難易度緩和として機能しないため、お題に紐づいた語を解禁する方式に改める。

#### 3.3.3. ワン・カタカナ

- 「ワン・カタカナ使用可能（自己申告制）」をルールとしてテキスト表記する。
- 出題者が「ワンカタカナで〇〇を使います」と口頭宣言して利用する。システム制御は行わない。

#### 3.3.4. パス券

- 出題者は、説明が困難と判断した場合にお題を放棄し、引き直すことができる。
- システム上は 3.2 の「引き直す」操作と同一。回数制限は口頭運用とする。

### 3.4. 口頭運用ルール（アプリ実装対象外）

アプリは実装しないが、ゲーム成立に必須のため本書に明記する。

#### 3.4.1. セッション内の重複

- 既に出題済みの単語が引かれた場合、**出題者が引き直す**。
- 参加者は同一の通話に参加しており既出語を共有しているため、システムによる管理は不要と判断する。システム化はフェーズ2（4.4）で扱う。

#### 3.4.2. 文字数の公開

- **お題のカタカナ表記の文字数は、常時公開してよい。** お助け機能（消費リソース）ではなく基本ルールとして扱う。
- 数え方は表記通りとする。**長音符「ー」および小書き文字（ャ・ュ・ョ・ッ 等）も1文字として数える。**
  - 例:「サーバーサイドレンダリング」は14文字。

#### 3.4.3. カタカナ・英語禁止

- カタカナ・英語を使わずにお題を説明する。
- **お題を日本語に訳した語も使用禁止とする。** 例:「Promise」に対する「約束」、「コールバック」に対する「呼び戻し」。表記をカタカナから漢字に置き換えただけの直訳は、言い換えの難しさというゲームの中核を回避してしまうため。
- 3.3.2 で解禁された語、および 3.3.3 で宣言した1語のみ例外とする。

#### 3.4.4. 正解判定

- アプリによる自動判定は行わない。口頭またはチャットで最も早く回答した者を正解とし、**出題者の裁量でジャッジする**。
- 表記揺れ（React / リアクト / React.js）の自動判定が困難なため。

#### 3.4.5. 失敗時の扱い

- 一定時間（目安30秒〜1分）経過しても正解が出ない場合、出題者が答えを開示して次の出題者に移る。
- MVPでは計測・制御は行わない。システム化の要否は 6.3 で扱う。

#### 3.4.6. 終了条件

- MVP段階では終了条件を設けず、任意のタイミングで終了とする。

## 4. 機能要件（フェーズ2: WANT）

**優先度は「ユーザー価値の大きさ」順に設定する。** v1では実装依存関係の順に並べていたため、リアルタイム同期を最優先としていたが、以下の理由で最後に移動した。

- v1でP1としていた同期対象（「誰が今出題中か」）は、参加者が同一の音声通話にいる時点で既に共有されている情報であり、限界価値が小さい。
- 一方、得点管理・終了判定はホストの手作業でしか成立しておらず、アプリ化による価値が大きい。

また **4.1〜4.3 → 4.4 の順序は必ず維持すること。** 同期対象となる状態モデルを確定してから転送手段を選定するためである。

### 【優先度: 高】 4.1. 得点・状態管理システム

ホストの端末上で動作するスコアボード機能として実装する（この時点では同期不要）。

- **スコア管理:** 難易度（1〜3）に応じたスコア設定、正解者・出題者へのポイント加算、ランキング表示。
- **参加者管理:** ゲーム開始時に参加者名を登録する。
- **お助け機能の使用状況管理:** 各参加者のお助け機能の所持数・使用済みステータスを保持し、使用済みの場合はボタンを非活性化する。
- **前提:** 本機能の設計時に、6.1〜6.3 の検討課題を解消しておく必要がある。

### 【優先度: 中】 4.2. ゲーム状態遷移の定義

4.1 の実装に伴い、ゲームの状態遷移を明示的に定義する。

- 想定される状態: `待機` → `お題ピック` → `出題中` → `判定（正解 / パス / 時間切れ）` → `次の出題者` → …→ `リザルト`
- 4.3・4.4 はいずれもこの定義に依存するため、先に確定させる。

### 【優先度: 中】 4.3. 終了条件のシステム制御

- ゲーム開始時に終了条件（例: n問先取、全員がn問出題、合計得点到達）を設定可能にする。
- 条件を満たした際、自動的にリザルト画面へ遷移する。

### 【優先度: 低】 4.4. リアルタイム同期（ルーム機能）

- **ルーム作成・参加:** ホストがルームを作成し、発行されたURLで他の参加者が入室できる。
- **役割別ビュー（必須）:** 出題者の画面にはお題が表示され、**他の参加者の画面にはお題がマスクされる**。同期を導入する場合、これが最も重要な要件となる。v1では記載が欠落していた。
- **状態同期:** 4.2 で定義した状態と、4.1 のスコア・使用済みステータスを全端末で同期する。
- **セッション内重複排除:** 共有状態として「出題済み単語リスト」を保持し、お題ピック時に抽出対象外とする（3.4.1 の口頭ルールを置き換える）。
  - **枯渇時の挙動を定義すること。** ピックは各難易度から1語ずつ抽出するため、いずれかの難易度が枯渇した時点で成立しなくなる。
- **技術選定:** 2.2 の通り、本項目の着手時に行う。
- **考慮事項:** 飲み会中の利用のため、端末のスリープ・回線断による切断が頻発する。再接続時の状態復旧と、出題者が離脱した場合のホストによる強制スキップ手段が必要になる。

### 【優先度: 低】 4.5. 回答機能のアプリ内実装（要検討）

- 表記揺れ（react / React.js / リアクト）を吸収できる仕組みが確立できた場合に、回答受付・自動判定機能の追加を検討する。
- 4.4 に依存する。

## 5. 非機能要件

- **レスポンシブ対応:** **スマートフォンでの利用を主とする。**
  - 各参加者が自端末でアプリを開く運用であり、PC画面は通話ツールで共有されている可能性があるため。PCブラウザでも操作可能とするが、優先度はスマートフォンが上位。
- **品質保証（テスト）:** お題データの `.ts` ファイルに対し、以下を保証する自動テスト（Vitest）を実装する。
  1. `id` および `word` に重複がないこと
  2. **各難易度（1・2・3）に最低件数以上の語が存在すること**（お題ピックは各難易度から1語ずつ抽出するため、いずれかが空だと機能が成立しない）
  3. `category` が定義済みの値であること
  4. **`relatedWords` に、当該お題の `word` と部分一致する語が含まれないこと**
- **状態の永続化:** 出題中のお題を `localStorage` に退避し、リロード・誤操作時に復帰できるようにする（優先度: 低）。

## 6. 検討課題（フェーズ2着手時に精査）

現時点では未解決だが、4.1（得点・状態管理）の設計時に必ず解消が必要な論点。

### 6.1. 難易度の定義

`difficulty: 1 | 2 | 3` は現状「語の知名度」ベースの暫定値である。以下の2軸が未分離であることを認識しておく。

- **(a) 和語・漢語のみで説明する難しさ**（出題者側の負荷）
- **(b) 回答者が当てる難しさ**（語のマイナーさ）

この2軸は一致しない。例えば「フレックスボックス」は (b) が高く (a) は低い。「アクセシビリティ」は語としてはマイナーでないが説明は容易である。

得点機能を導入する際、**加点対象（正解者 / 出題者）と難易度がどちらの軸を指すのか**を先に決める必要がある。(a) を指すなら出題者への加点が、(b) を指すなら正解者への加点が正当化される。

### 6.2. 選択機構の退化リスク

難易度連動スコアを導入し、かつ失敗時のペナルティが存在しない場合、**「常に難易度3を選ぶ」が支配戦略**となり、3つの候補から1つを選ぶというMVPの中核メカニクスが機能しなくなる。

高難易度に何らかの失敗リスク（時間切れによる減点、パス時の出題権消費など）を紐づけるかどうかを、スコア設計と同時に決めること。

### 6.3. 失敗状態のシステム化

MVPでは 3.4.5 の口頭ルールで運用するが、得点を導入する場合は以下を確定する必要がある。

- 制限時間を設けるか（設ける場合、アプリでタイマーを提供するか）
- 時間切れ時の出題者・回答者の得点をどうするか
- パス（3.3.4）と時間切れを区別するか

### 6.4. 判定者の利害

出題者は正解判定の裁量を持ちながら、正解成立時に加点される立場でもある。飲み会用途では実害は想定しにくいが、得点を厳密に扱う場合は構造上の論点として認識しておく。

## 7. その他の留意事項

- 「ボブジテン」は市販ボードゲームの商品名である。公開URL上でこの名称を冠する場合、商標上の配慮が必要になる可能性がある。私的利用の範囲であれば実害は小さいと考えられるが、公開範囲は意識しておくこと。
