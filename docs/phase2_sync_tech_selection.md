# フェーズ2 技術選定: 同期レイヤ

## 1. 結論

**Cloudflare Workers + Durable Objects（SQLite バックエンド）+ WebSocket Hibernation API** を採用する。

---

## 2. 選定の決め手

コスト・スケール・知名度ではなく、**設計書 6.2「情報の公開範囲」を満たせるか**が実質的な唯一の判断軸になった。

出題中は、出題者にはお題を送り、他の参加者にはマスクした情報のみを送る必要がある。**同一ルームの接続ごとに異なるペイロードを配信できること**が必須条件であり、これを満たさない選択肢は他の条件をどれだけ満たしても不採用となる。

Durable Objects はルーム単位のオブジェクトが全接続を保持し、接続ごとにメタデータ（誰の接続か）を紐づけて個別に送信できるため、この条件を素直に満たす。

副次的な利点として、`reduceSession` をサーバ側でそのまま実行できる。クライアントとサーバでゲームロジックが二重化せず、設計書 6.1 の実行主体検証（`canPerform`）もサーバ側で同じコードを使える。

---

## 3. 見送った選択肢と理由

| 選択肢 | 見送りの理由 |
| --- | --- |
| Supabase Realtime | ブロードキャスト前提で、接続ごとに内容を変える機能がない。マスクを実現するにはサーバ層を別途立てることになり、Durable Objects を使うより複雑になる |
| Firebase | セキュリティルールで読み取り範囲を制限できるが、ゲームロジックがクライアント側かクラウド関数側に分かれる。`reduceSession` を共有する構成が崩れる |
| Liveblocks 等の共同編集基盤 | 全員が同じドキュメントを見る前提の設計であり、参加者ごとの情報秘匿という要求と噛み合わない |
| 自前サーバ（Fly.io 等） | 実現可能だが、無料での常時稼働が保証されず、休止からの復帰も挟まる。運用の手間に見合わない |

---

## 4. コスト試算

無料枠に収まる。試算の前提は1セッション90分・7名・操作200回程度。

**リクエスト（無料枠 100,000 / 日）**
WebSocket の受信メッセージは 20:1 の比率で課金換算される。1セッションの操作数は数百程度なので、換算後は数十リクエスト。無視できる。

**実行時間（無料枠 13,000 GB-s / 日）**
Durable Object には 128 MB が割り当てられ、実使用量に関わらずその値で課金される。仮に Hibernation を使わず90分間接続を保持し続けても約 690 GB-s であり、1日の無料枠の5%程度。**Hibernation を使えばアイドル時間は課金対象外**になるため、さらに余裕がある。

**ストレージ**
SQLite ストレージ課金は2026年1月に有効化されたが、**Workers Free プランでは課金されない**。

**上限超過時の挙動**
無料プランでは、いずれかの上限を超えた時点でその種類の操作がエラーになる。**課金へ移行するのではなく停止する**ため、意図しない請求が発生しない。「ランニングコスト完全無料」という当初の要件が構造的に保証される。

## 5. 構成上の判断

### 5.1. WebSocket Hibernation API を使う

接続を保持したまま Durable Object を休止させられる。コスト上の必要性は上記のとおり高くないが、**アイドル中に課金が発生しない構成のほうが、上限超過による停止リスクを下げられる**ため採用する。

代償として、休止中はメモリ上の状態が失われる。したがって**状態遷移のたびにストレージへ永続化し、復帰時に読み戻す**必要がある。

### 5.2. 状態は JSON 1件として保存する

`SessionState` は7名分の得点と進行状態のみで、数 KB に収まる。SQL テーブルへ正規化せず、**状態全体を1件のレコードとして保存・読み出しする。**

理由は、部分更新のためのスキーマ設計とマイグレーションのコストが、この規模では利益を上回るため。状態遷移が `reduceSession` で完結している以上、差分更新の必要がない。

### 5.3. クライアントへは常に状態全体を送る

差分配信は行わない。ペイロードが小さいため、**毎回スナップショットを送るほうが、差分の適用漏れという不具合の種類そのものを消せる。**

再接続時の復元も、通常の配信と同じ経路になる。特別な復元処理を書かずに済む。

### 5.4. ルームは名前で識別する

短いルームコードを URL に含め、それを Durable Object の名前として解決する。コードを知っている全員が同じオブジェクトに接続する。

### 5.5. デプロイ構成は変わらない

現在は Worker スクリプトを持たない静的アセット配信のみだが、そこに Worker 本体と Durable Object の定義を追加する形になる。**Cloudflare Pages ではなく Workers を選んでいたため、デプロイ先を分けたり構成を二重化したりする必要がない。**

## 6. 実装前に決めるべきこと

### 6.1. なりすまし対策

ルームコードを知っていれば誰でも接続できる。参加者の識別を自己申告の ID のみで行うと、**出題者になりすまして自分にお題を送らせることが可能**になる。設計書 6.2 の秘匿要件が破れる。

対策の選択肢は以下。

* **A: 入室時にサーバが秘密トークンを発行し、クライアントが保持する。** 以降の操作はトークンで本人確認する。再接続時もトークンを提示する
* **B: 対策しない。** 参加者は既知の7名であり、なりすましは実質的に起こらないと割り切る

**A を推奨する。** 実装コストは小さく（入室時に乱数を1つ発行して保存するだけ）、再接続時の本人特定にも同じ仕組みを使えるため、B を選んでも結局似たものが必要になる。

### 6.2. ルームの寿命

ゲーム終了後にルームをいつ破棄するか。無期限に保持するとストレージが増え続ける。

Durable Objects のアラーム機能で、一定時間（例: 最終操作から24時間）操作がなければ状態を削除するのが素直。**この判断は設計書 5章への追記が必要。**

### 6.3. 再接続と離脱の振る舞い

設計書 5.6 は強制スキップに触れているが、以下が未定義。

* 離脱者が戻ってきたときの扱い（同じ ID で再入室できるか）
* 出題者が離脱している間、他の参加者の画面に何を表示するか
* ホストが離脱した場合、ホスト権限を移譲するか

**実装前に設計書へ追記すること。**
